# theoria

A component explorer for Leptos, Storybook in miniature: a crate writes
"stories" (named previews of its components, with editable args), and the
`theoria` CLI generates and serves a gallery that shows them one at a time.
Three published crates and one test crate:

- `crates/theoria`: the gallery components and `Story`.
- `crates/theoria-macros`: `#[story]`, which turns a function's typed
  parameters into live controls and captures its source and doc comment.
- `crates/theoria-cli`: the `theoria` binary (`serve`, `build`,
  `generate`), which writes a Trunk app under `target/theoria/gallery`
  from a `theoria.toml` and runs Trunk on it. Its `main` only calls the
  library's `theoria_cli::run`.
- `crates/theoria-e2e` (outside the workspace): builds a gallery from
  theoria's own components (`theoria-e2e.toml`) and drives it in Chromium
  with playwright-rs.

The plan and the backlog are in `crates/theoria/docs/PLAN.md` and
`crates/theoria/docs/stories/`. A story or slice is built when a consumer
needs it, not before. theoria's components are tested with leptotes, never
by previewing theoria inside theoria.

## Development

```bash
cargo build              # build
cargo nextest run        # run tests
cargo test --doc         # doc tests
cargo clippy             # lint
cargo fmt                # format
cargo deny --workspace check bans licenses sources  # licenses, bans, sources
cargo deny --workspace --config deny.toml --manifest-path crates/theoria-e2e/Cargo.toml check bans licenses sources  # the same, on the e2e crate
prek run cargo-lockpatrol --all-files  # advisories in every tracked Cargo.lock (ignore list: deny.toml)
cargo vet                # supply chain review
```

The gallery and its browser tests need the wasm target and Trunk (once
per machine: `rustup target add wasm32-unknown-unknown`, `cargo install
trunk`), and the Chromium revision the locked playwright-rs expects, which
the first line below installs (again after a playwright-rs bump):

```bash
cargo run --manifest-path crates/theoria-e2e/Cargo.toml --example install-browsers
cargo run -p theoria-cli -- serve --config theoria-e2e.toml  # theoria's own stories on :8081
cargo run -p theoria-cli -- build --config theoria-e2e.toml  # build the e2e gallery
cargo nextest run --manifest-path crates/theoria-e2e/Cargo.toml --config-file .config/nextest.toml --run-ignored all  # drive it in Chromium
cargo clippy --manifest-path crates/theoria-e2e/Cargo.toml --all-targets -- -D warnings
```

A session runs the e2e tests with the `cargo nextest run` line above, as
the first command of its own Bash call, which the sandbox's `cargo nextest
run *` exclusion covers. `cargo test` on the same crate is sandboxed, and
Chromium dies at launch (`bootstrap_check_in ... Permission denied`). Every
e2e test is `#[ignore]`d, since it needs the built gallery and all but the
lockfile check need Chromium:
without `--run-ignored all` nextest exits with "no tests to run", and with
it a test fails, naming the build command, when the gallery is missing.

`serve` rebuilds on any change under the stories crate's `src/`, which the
generated `Trunk.toml` watches (theoria's own, for `theoria-e2e.toml`). A change to the
config file or to `Cargo.lock` needs a re-run, because the harness is
generated once at start, with a copy of the lockfile.

## Claude Code sandbox

The sandbox is on in user settings for every repo, and a session never
writes outside its own working tree. There is no per-repo sandbox file
to look for.

## Pre-commit hooks

```bash
cargo install prek
prek install --overwrite   # --overwrite replaces any legacy pre-commit hook
```

Hooks mirror CI checks: fmt, clippy, check, nextest, doctest, deny, vet,
and the skill version guard.

Before a session's first commit in a clone, it checks that
`.git/hooks/pre-commit` exists and that its second line reads
`# File generated by prek`. If either fails, the session stops and asks
the user to run `prek install --overwrite` from a plain terminal: the
install writes `.git/hooks`, which the sandbox protects. A commit made
without the hook goes in unchecked and nothing reports it, so a session
never says hooks ran on a commit it has not checked this way.

Run `prek` as the first command of its own Bash call. `prek` is in the
sandbox's `excludedCommands`, which match only the command that starts
the call, so `git add -A && prek run --all-files` runs prek sandboxed and
`end-of-file-fixer` fails opening `.claude/settings.json`.

## Manual checks

What a session cannot check and the person reviewing the work can. A
hand-off before a commit names each one that applies, as its command and
what a pass looks like; CI is the backstop, not the plan.

**From a plain terminal** (the sandbox blocks these):

- The pre-commit hook, once per clone: `prek install --overwrite`. A pass
  is `.git/hooks/pre-commit` with `# File generated by prek` as its second
  line.
- A change to `.claude/settings.json`: the sandbox denies writes to it,
  so apply the edit by hand, then run `/sandbox` in a new session. A pass
  is the resolved config showing the change.
- A change to the contributor skill: copy the session's draft into
  `.claude/skills/theoria-dev/`. A pass is `git status` showing the file
  as modified or new, not ignored.
- A new consumed skill: `npx skills add <owner>/<repo>` (Agent skills,
  below). A pass is one entry per skill in `ls -l .claude/skills/`.
- A new public API's rustdoc: `cargo doc --open`, since `open` is blocked
  in the sandbox.
- The GitHub settings, until the release ceremony deletes the script:
  `./scripts/github-settings.sh` (`--apply` to set what is off), after
  setup and after any change to the required checks or release tags
  (SETUP.md, "GitHub settings", lists what it sets). A pass is exit 0
  with only `ok` and `manual` lines. A session never runs it: these are admin
  changes, and its `gh` calls fail in the sandbox on purpose.

**Not from a session at all**, changed on github.com or crates.io:
creating the merge App, installing it on the repo and generating its key,
Dependabot malware alerts, and the crate's Trusted Publisher.

**By eye:**

- Prose a reader will act on: the CHANGELOG entry, README, the setup
  checklist while there is one, and the shipped skill under `skills/`.
  The skill version guard checks the bump, not that the prose is still
  true.
- A workflow change: the first run of the changed job on GitHub, since
  nothing local runs it. A job that only fires on a tag, a schedule or a
  Dependabot PR waits for that event, or a `workflow_dispatch` where it
  has one.

## Agent skills

`.claude/skills/theoria-dev/` is the contributor skill: the crate split,
how components, stories, and tests are wired, what each kind of test and
mutation testing covers, the CLI's harness, the backlog, and the release
order. It is tracked, Claude Code loads it in every session here, and it
is never shipped. The sandbox denies writes under `.claude/skills/`, so a
session drafts a change to it elsewhere and you copy it in.

`skills/theoria-usage/` is the skill theoria will ship to crates that
write stories. It stays hidden from installers (`metadata.internal: true`)
until the API settles. Edits to it must bump `metadata.version` in its
`SKILL.md`; the pre-commit hook and the `Skill version guard` CI job both
enforce that.

Skills of tools this crate depends on are managed installs, not vendored:
`skills-lock.json` (tracked) records each source and a content hash, and
`npx skills add <owner>/<repo>` fetches the content into `.agents/` and
links it from `.claude/skills/`. Both paths are gitignored, so run the
installs once after cloning, from a plain terminal (the sandbox denies
writes under `.claude/skills/`). Verify with `ls -l .claude/skills/`: one
entry per installed skill. Refresh with `npx skills update -p`: without
`-p` it prompts for a scope and defaults to Global. The refresh runs fine
inside the sandbox, since the real files live under `.agents/`; only
`add`, which creates the `.claude/skills/` symlink, needs a plain
terminal. Confirm by reading `metadata.version` out of the installed
`SKILL.md`.

## Mutation testing

```bash
./scripts/mutants.sh                 # diff HEAD~1..HEAD (default)
./scripts/mutants.sh main            # diff main..HEAD
./scripts/mutants.sh --working       # diff uncommitted edits against HEAD
./scripts/mutants.sh -- --jobs 4     # pass extra cargo-mutants args
```

`scripts/mutants.sh` wraps `cargo mutants --in-diff`, scoping mutation
testing to just the lines a commit touched. A full-codebase run grows
linearly with codebase size and routinely takes hours; `--in-diff`
keeps the loop fast enough to use while the test is still warm. Use
`--working` to gate edits before committing them (new files need
`git add -N <file>` first to show up in the diff). Don't reach for
`cargo mutants -f <file>` as the fast path: with `examine_globs` set it
ignores the filter and sweeps everything in scope.

Run one mutation job at a time; every run writes `mutants.out/`. A
stray run is stopped with `pkill -f cargo-mutants` (hyphen; the binary
is `cargo-mutants`).

CI runs the per-diff variant on every push and PR, and the full-codebase
sweep only on `workflow_dispatch` — use it for occasional audits or big
refactors, never on a schedule. Both come from `security.yml`'s
`mutation` job, which calls `mutation.yml` in `padamson/rust-ci-workflows`.
The CI diff job computes its own diff and runs `cargo mutants --in-diff`
directly, not this script.

Scope the baseline with `.cargo/mutants.toml`, which ships live (a
`.mutants.toml` at the repo root is ignored silently); `--in-diff`
narrows from there.

## Tests

A test is a claim about behavior, named as the claim, one claim per
test, asserting the value rather than prose: `assert_eq!` on a story's
name and args, `matches!` on an `ArgControl` variant, the rendered HTML
from `leptotes::render`. Components live in `src/components/` as
`<name>.rs`, with `<name>.stories.rs` (behind the `stories` feature) and
`<name>.tests.rs` beside it. A test that needs something a fresh clone may
lack is gated with `#[ignore = "reason; run with ..."]`. Never `return`
from a test because a precondition is missing.

`.config/nextest.toml` bounds every test with a slow-timeout; the hook
runs the default profile (no retries) and CI runs `--profile ci` (one
retry, reported FLAKY). nextest does not run doctests, so `cargo test
--doc` is its own step, and the crate keeps at least one doctest so that
step is not a no-op.

## Release process

1. Update version in `Cargo.toml`
2. Update `CHANGELOG.md`
3. Commit: `git commit -m "Release vX.Y.Z"`
4. Tag: `git tag vX.Y.Z`
5. Push: `git push origin main --tags`

The tag triggers CI, which checks each crate's semver against its latest
crates.io release, then builds and tests while it runs `cargo deny` and
`cargo vet` on the tagged commit (by calling the shared `supply-chain.yml`
that `security.yml` also calls), publishes
to crates.io only once both have passed, and creates a GitHub Release.
A crate not yet on crates.io skips the semver check, and a version
already there skips the publish; any other answer from crates.io fails
the run, and so does a tag that no publishable crate's version matches.

A crate's first version is published by hand, since crates.io adds a
trusted publisher only to a crate that exists. Then add `[policy.<crate>]
audit-as-crates-io = false` to `supply-chain/config.toml`, commit it, and
tag that commit, not the one you published from. Without the policy,
`cargo vet` matches the path crate to its crates.io version and fails
every push, and the tag's vet gate with it. The tag's run then finds the
version on crates.io, skips the publish, and creates the GitHub Release.
A crate new to the workspace gets the same order.

`theoria` depends on `theoria-macros` through crates.io once published, so
the first versions go out by hand in the order `release.yml` uses:
`theoria-macros`, then `theoria`, then `theoria-cli`.
